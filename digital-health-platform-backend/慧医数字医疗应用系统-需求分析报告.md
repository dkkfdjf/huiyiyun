# 慧医数字医疗应用系统 需求分析报告

---

## 1. 项目概述

### 1.1 项目背景

在医疗领域中,医疗信息的完整与规范是提升诊疗服务效率与质量、改善患者康复效果的关键环节。然而当前医疗信息系统普遍存在以下痛点:

- **医生资源分配不均**:科室人力失衡,缺乏数据化调配依据;
- **药物销售流程繁琐**:药品铺货、销售、补货、库存预警靠人工台账,易错且低效;
- **无法可视化管理**:网点覆盖范围、医师地理分布等缺乏直观的地图化呈现;
- **信息不对称**:医药公司政策、药品信息难以高效触达医疗机构与医师。

本项目旨在设计开发一款基于 **Spring Boot + Vue** 的**慧医数字医疗应用系统**,通过系统化、信息化的方式,实现医师资源管理、药品供应链管理(铺货—销售—补货—预警)、医药公司政策与必备材料管理,并以地图可视化辅助管理决策。

### 1.2 项目目标

1. 实现医药公司、药品、销售网点、医师、医疗机构等核心资源的数字化管理;
2. 构建从药品录入、网点铺货到销售出库、补货入库、库存预警的**完整业务闭环**;
3. 提供角色化的数据概览与**地图可视化**(销售点标注、医师地理分布),辅助管理决策;
4. 通过行级数据隔离,保障各医药公司、各医疗机构的数据互不越权。

### 1.3 系统范围界定

- **本期聚焦**:药品供应链管理(药品 / 库存 / 销售 / 补货)、医师资源管理、医药公司及政策管理、必备材料管理、地图化数据概览。
- **本期不含**:电子病历(EMR)、在线诊疗/处方流转、医保实时结算、患者端等临床与结算功能(相关外部接口均标注为二期扩展)。

## 2. 运行环境需求

本系统采用 **B/S 架构**,基于 Spring Boot + Vue 技术栈开发,客户端通过浏览器访问,应用服务与数据服务分层部署。

### 2.1 客户端

| 项目 | 要求 |
|---|---|
| 体系结构 | B/S 架构,浏览器访问 |
| 浏览器 | Chrome / Edge / Firefox / Safari 主流版本(支持 HTML5) |
| 屏幕分辨率 | 1366×768 及以上,推荐 1920×1080 |
| 网络 | 建议带宽 ≥ 2Mbps |

### 2.2 应用服务器端

| 项目 | 要求 |
|---|---|
| 运行环境 | **JDK 17 (LTS)** |
| 应用框架 | **Spring Boot 3.2.x**(内置 Tomcat) |
| 前端框架 | **Vue 3 + Vite** |
| 中间件 | Redis(会话存储 / 数据缓存 / 库存预警状态) |
| 部署方式 | **单机部署为主,架构支持水平扩展**(Nginx 反向代理;预留多实例负载均衡能力) |
| 硬件建议 | CPU 4 核+,内存 8 GB+,SSD 200 GB+ |

> 说明:本期数据量较小(销售网点百级、库存记录千级),单机即可满足性能要求;采用无状态服务 + Redis 统一会话设计,后续可平滑扩展为多实例集群。

### 2.3 数据库服务器端

| 项目 | 要求 |
|---|---|
| 数据库 | **MySQL 8.0+**(兼容 5.7+) |
| 字符集 | utf8mb4(支持中文及特殊字符) |
| 存储引擎 | InnoDB(支持事务与行级锁) |
| 备份策略 | 每日全量备份,保留 30 天 |

## 3. 产品的功能性需求

### 3.1 角色定义

本系统共设 **四类角色**:

| 角色 | 定位 |
|---|---|
| **系统管理员** | 平台运维、基础数据、账号与权限、医药公司账号审核、全局数据概览 |
| **医药公司用户** | 管理本公司业务(公司信息、政策、药品、库存与销售、销售地点) |
| **医疗机构管理员** | 管理本院医师资源(增删改、分配科室、重置密码),查询药品/政策/材料 |
| **医师(普通用户)** | 浏览查询个人信息、药品 / 政策 / 材料公告 |

### 3.2 整体业务流程

#### 3.2.1 用户登录与权限分流

- **使用者**:系统管理员 / 医药公司用户 / 医疗机构管理员 / 医师(普通用户)
- **目的**:登录系统并根据角色身份进入不同的功能主页。

**基本事件流:**

1. 使用者打开系统首页,点击"登录",本用例开始;
2. 系统显示登录界面(含**图形验证码**);
3. 使用者输入用户名、密码及验证码,点击"登录";
4. 系统校验验证码并核对账号信息:
   - 若账号正确且为**系统管理员** → 进入全局数据概览主页;
   - 若为**医药公司用户** → 进入本公司业务管理主页(仅本公司数据);
   - 若为**医疗机构管理员** → 进入本院医师管理主页(仅本院数据);
   - 若为**医师** → 进入个人工作台主页;
5. 本用例结束。

**备选事件流:**

- 4a. 验证码错误:提示"验证码错误",刷新验证码;
- 4b. 账号或密码错误:提示"用户名或密码错误",返回登录界面;
- 4c. 账号被禁用 / 待审核:提示"账号不可用,请联系管理员";
- 4d. 连续输错密码 5 次:锁定账号 30 分钟并记录日志。

#### 3.2.2 药品供应—销售业务闭环(核心主线)

系统以医药公司为中心,形成"铺货 → 销售 → 扣减 → 预警 → 补货"的**供给侧闭环**,并经医师"临床用药反馈"补上**需求侧反向闭环**,直接解决"药物销售流程繁琐""无法可视化管理""药品需求信息不对称"三大痛点:

```
①[医药公司] 录入药品基本信息(名称/规格/剂型/所属公司)
        ↓
②[医药公司] 维护销售地点(网点) + 关联城市 + 地图选点(经纬度) + 设定【售价 + 初始库存】(铺货)
        ↓
③[医药公司] 销售登记(出库):选药品+数量+销售地点 → 系统自动扣减该网点库存
        ↓  库存 ≤ 阈值 → 数据概览红色预警
④[医药公司] 补货:入库登记 → 库存回升                          (库存回升,回流至 ③ 继续销售)
        ↓
⑤[医疗机构管理员/医师] 查询可售药品、库存、政策(只读消费) ── 闭环终点:赋能医疗机构与医师
        ↓  基于临床用药情况
⑥[医师] 提交临床用药反馈(临床用药需求 / 临床用量反馈)
        ↓  临床反馈流转至对应医药公司
⑦[医药公司] 汇总临床反馈、识别用药趋势 → 据此补货 / 铺货 / 调整供应              (趋势驱动,回流到 ②④,形成临床需求→供给反向闭环)
```

> 〔系统外受益方:患者〕诊疗与用药更规范。患者**不是系统角色**,不纳入系统功能,仅作为系统价值的外部落脚点。

### 3.4 功能类别 A —— 核心业务功能

#### 3.4.1 主页面数据概览(角色化数据看板)

不同角色登录后看到不同层级的看板,**统计图表采用 ECharts,地理分布采用高德地图**(详见第 5 章)。看板数据经 **Redis 缓存优先提供**:项目启动时从数据库预热热点数据到缓存,首页查询优先命中缓存以保障加载性能(详见详细设计 6.6)。

| 角色 | 看板内容 |
|---|---|
| 系统管理员 | 全国总数(医疗机构/药品/合作企业/销售地点)、**医师地理分布地图**(按医师所属医疗机构聚合)、医师职称分布、医师科室分布、最新医药公司政策、待审核公司数 |
| 医药公司用户 | 本公司药品数、覆盖销售点数、**销售点地图标注**、库存预警列表、**待处理临床用药反馈数**、销售统计图表、政策发布数 |
| 医疗机构管理员 | 本院医师数、科室人员分布、可售药品查询 |
| 医师 | 个人信息(可自助修改联系方式)、药品 / 政策 / 材料公告、**我提交的临床用药反馈及处理状态** |

> 医师可在个人工作台自助修改本人联系方式(手机号、邮箱),修改即时生效;本期不强制二次验证(验证码体系见 4.6)。

#### 3.4.2 医师管理(使用者:医疗机构管理员)

| 子功能 | 说明 |
|---|---|
| 新增医师 | 录入医师基本信息及**所属医疗机构、科室** |
| 修改医师信息 | 更新医师资料 |
| 删除医师 | 逻辑删除(保留历史记录) |
| 分配科室医师 | 调整医师所属科室,平衡科室人力,缓解"医生资源分配不均" |
| 重置密码 | 管理员为医师重置初始密码(**仅限本院医师**,操作记录审计日志) |

> 医师作为系统可登录用户,其账号与医师档案一一对应(详见第 6 章数据实体)。

**用例:分配科室医师**

- **使用者**:医疗机构管理员
- **目的**:将医师调配至目标科室,均衡各科室人力资源。
- **前置条件**:医师与科室均已建档。
- **基本事件流:**
  1. 进入"医师管理 → 分配科室";
  2. 选择待调配医师与目标科室;
  3. 系统校验目标科室是否存在;
  4. 系统更新医师科室归属,记录变更日志;
  5. 看板科室分布数据刷新,本用例结束。
- **备选事件流:** 3a. 目标科室不存在:提示并中止。

#### 3.4.3 医药公司管理(使用者:医药公司用户 / 系统管理员)

包含四部分:**公司账号审核**(系统管理员)、**公司信息维护**(增删改查)、**政策维护**(对医保 / 药企政策增删改查)、**发展查询**(查询公司发展情况)。医药公司用户仅能操作本公司数据。

| 子功能 | 说明 | 使用者 |
|---|---|---|
| 添加医药公司 | 录入公司基本信息,状态为"待审核" | 系统管理员 |
| 医药公司审核 | 审核/驳回待审核的医药公司账号,通过后账号方可登录 | 系统管理员 |
| 修改 / 删除 / 查询医药公司 | 维护公司基本信息 | 系统管理员 |
| 本公司信息维护 | 医药公司用户维护本公司信息 | 医药公司用户 |
| 政策维护 | 对本公司医保 / 药企政策增删改查 | 医药公司用户 |
| 发展查询 | 查询本公司**药品数、销售点覆盖数、销售趋势、政策发布数**等发展指标 | 医药公司用户 |

**用例:医药公司账号审核**

- **使用者**:系统管理员
- **目的**:审核新注册的医药公司账号,通过后账号方可正常使用系统。
- **前置条件**:存在待审核状态的医药公司记录。
- **后置条件**:`pharma_company.audit_status` 更新为"正常 / 驳回 / 停用"之一(四态:`0待审核/1正常/2驳回/3停用`)。

**基本事件流:**

1. 进入"医药公司管理 → 待审核列表";
2. 系统显示所有 `audit_status=0(待审核)` 的公司;
3. 选择一条记录,查看公司详情(名称、信用代码、执照号等);
4. 点击"审核通过"或"审核驳回":
   - **通过**:更新 `audit_status=1(正常)`,向联系人发送通知;
   - **驳回**:更新 `audit_status=2(驳回)`,要求填写驳回原因(与"停用"语义区分:驳回=审核未过,可整改后重新提交);
5. (可选)曾通过的公司可被**停用**:`audit_status=3(停用)`,账号无法登录,可再恢复为正常;
6. 刷新待审核列表,本用例结束。

**用例:发布医药公司政策**

- **使用者**:医药公司用户
- **目的**:发布本公司最新药品 / 价格 / 医保政策,供医院与医师查阅。
- **基本事件流:**
  1. 进入"医药公司管理 → 政策管理 → 新增";
  2. 填写政策标题、内容、生效日期;
  3. 系统校验字段完整性;
  4. 保存并发布,系统在数据概览"最新政策"区域同步展示;
  5. 本用例结束。

#### 3.4.4 药品信息管理(使用者:医药公司用户)

| 子功能 | 说明 |
|---|---|
| 录入 / 修改 / 删除 / 查询药品 | 维护药品基本信息(名称、规格、剂型、所属公司、批准文号) |
| 药品上下架 | 切换药品 `status`(上架/下架);**下架后不可被销售登记选中**,历史销售/库存记录保留 |
| 库存初始化(铺货) | 为新销售地点设置可售药品及初始库存量、售价、预警阈值 |
| 维护库存与售价 | 修改"药品 × 销售地点"维度的库存量、销售价格、预警阈值 |
| 库存查询 | 查询各网点药品库存情况,支持按药品/网点筛选 |
| 销售登记(库存扣减) | 记录销售并自动扣减库存,生成销售单流水 |
| 入库登记(补货) | 补货入库,增加库存,生成补货单流水 |
| 库存预警列表 | 展示所有低于预警阈值的库存记录,支持一键预警通知 |
| 销售记录查询 | 查询历史销售记录,支持按日期/药品/网点筛选 |

**用例:库存初始化(铺货)—— 业务起点**

- **用例编号**:UC-A04-1
- **使用者**:医药公司用户
- **目的**:为新开设的销售地点设置可售药品及初始库存,完成业务闭环的第一步"铺货"。
- **前置条件**:已存在本公司的销售地点记录。
- **后置条件**:`drug_stock` 新增记录。

**界面输入字段:**

| 字段 | 类型 | 必填 | 校验规则 | 说明 |
|---|---|---|---|---|
| 销售地点 | 下拉选择 | 是 | 仅本公司网点 | |
| 药品 | 下拉选择 | 是 | 仅本公司药品 | |
| 初始库存量 | 数字 | 是 | ≥0 | |
| 销售价格 | 数字 | 是 | >0 | 保留两位小数 |
| 预警阈值 | 数字 | 否 | ≥0,默认0 | 低于此值预警 |

**基本事件流:**

1. 进入"库存管理 → 铺货初始化";
2. 选择销售地点与药品;
3. 填写初始库存量、销售价格、预警阈值;
4. 系统校验该"药品×地点"组合是否已存在库存记录;

**用例:销售登记(库存自动扣减)—— 核心闭环**

- **用例编号**:UC-A04
- **使用者(参与者)**:医药公司用户(主参与者)、系统(次参与者,负责自动扣减)
- **目的**:记录销售地点的药品销售,系统自动扣减对应库存,规范销售流程,解决"药物销售流程繁琐"痛点。
- **前置条件:**
  1. 用户已登录且角色为医药公司用户;
  2. 已存在本公司的销售地点;
  3. 目标药品在该销售地点存在库存记录(`drug_stock`)且库存量 > 0。
- **后置条件**:`sales_record` 新增一条记录;`drug_stock.stock_qty` 减少;若触发阈值则数据概览预警。

**界面输入字段:**

| 字段 | 类型 | 必填 | 校验规则 | 说明 |
|---|---|---|---|---|
| 销售地点 | 下拉选择 | 是 | 仅本公司网点 | 选择后加载可售药品 |
| 药品 | 下拉选择 | 是 | 该地点可售 | |
| 销售数量 | 数字 | 是 | 正整数,≤当前库存 | |
| 单价 | 自动带出 | 是 | > 0 | 取 `drug_stock.price`,可改 |
| 总金额 | 自动计算 | — | = 数量 × 单价 | 只读 |
| 销售时间 | 日期时间 | 是 | 默认当前时间 | |
| 备注 | 文本 | 否 | ≤200 字 | |

**基本事件流(主流程):**

1. 用户进入"销售登记"页面;
2. 选择销售地点,系统加载该地点可售药品列表及当前库存;
3. 选择药品,输入销售数量;
4. 系统自动带出单价并计算总金额;
5. 用户点击"确认销售";
6. 系统校验:库存是否充足、字段是否合法(见备选流);
7. 校验通过,**开启数据库事务**:
   1. 向 `sales_record` 插入一条销售记录;
   2. 对应 `drug_stock.stock_qty` 扣减销售数量(`UPDATE ... WHERE stock_qty >= ?`,防超卖);
8. 判断扣减后库存是否 ≤ 预警阈值 `threshold`:若是,生成/更新数据概览预警;
9. 提示"销售成功",刷新库存显示,本用例结束。

**备选事件流:**

- 6a. **库存不足**:提示"库存不足,当前仅剩 X 件",禁止提交,返回步骤 3;
- 6b. **字段非法**(数量 ≤ 0、非整数、单价 ≤ 0):提示具体错误,返回步骤 3;
- 6c. **会话失效**(Token 过期):跳转登录页,要求重新登录;
- 7a. **事务失败**(并发扣减导致行冲突):事务回滚,提示"操作失败,请重试",返回步骤 5。

**业务规则:**

1. 库存维度为"**药品 × 销售地点**",不同网点的同种药品库存相互独立;
2. 扣减须在**数据库事务**中完成,配合乐观锁/条件更新,**杜绝超卖**;
3. **数据隔离**:医药公司用户仅能查询与销售本公司的网点与药品;
4. 预警阈值 `threshold` 可由医药公司自行设置,默认为 0;
5. 销售记录不可删除,仅可查询/统计,保证审计可追溯。
6. **进销存台账**:`sales_record`(出库)与 `replenishment_order`(入库)共同构成"药品 × 销售地点"维度的进销存流水,系统提供按药品、按网点、按时间维度的进销存汇总查询(累计入库量、累计销售量、当前库存)。

#### 3.5.4 数据删除与逻辑删除策略

删除操作按表分类处理,**不采用"全部软删除"**:

| 表类别 | 策略 | 涉及实体 |
|---|---|---|
| 主数据 / 业务实体 | **逻辑删除**(软删除) | user、pharma_company、medical_institution、doctor、drug、sales_location、city、essential_material、company_policy、drug_stock、drug_demand |
| 流水表 | **只增不删**(append-only),不提供删除操作 | sales_record、replenishment_order |
| 日志表 | **按保留期定时物理清理** | login_log / operation_log / error_log(见 4.5) |

**逻辑删除实现约定**(主数据表统一):

- 加 `deleted TINYINT NOT NULL DEFAULT 0`(0 正常 / 1 已删除),配合 MyBatis-Plus `@TableLogic` 自动过滤已删除数据,业务代码无需手写条件;
- 配套审计字段 `create_time`、`update_time`、`create_by`、`update_by`;
- **唯一约束处理**:涉及唯一性的字段(如 `drug.approval_no`、`user.username`)采用**联合唯一索引** `UNIQUE(字段, deleted)`,避免软删一条后无法新增同名记录。

**引用约束**(软删除时校验):

| 被删除对象 | 约束规则 |
|---|---|
| 城市 | 存在销售地点 / 医疗机构引用时禁止删除 |
| 医药公司 | 关联的药品、网点、库存、政策一并标记删除(或禁止删除) |
| 药品 | 存在有效库存记录时禁止删除 |
| 销售地点 | 存在有效库存记录时禁止删除;逻辑删除后其库存记录一并标记删除,**历史销售 / 补货流水保留**,不影响审计追溯 |
| 销售记录 | **不可删除**,仅可查询,保证审计可追溯 |
| 临床用药反馈 | 可由提交医师撤回,或医药公司标记"已满足 / 已驳回";逻辑删除保留历史,审计可追溯 |

## 4. 产品的非功能性需求

### 4.1 用户界面需求

1. 采用响应式布局,适配主流分辨率与终端(PC 为主,兼容平板);
2. 整体风格简洁专业,符合医疗行业稳重观感,主色调统一;
3. 导航层级清晰,核心操作(销售登记、库存预警)入口不超过 2 级;
4. 统计图表采用 **ECharts**(柱状图、饼图、分布图),地理分布采用**高德地图**组件;
5. 关键操作(删除、销售)提供二次确认,避免误操作;
6. 操作成功 / 失败时,2 秒内给出明确提示。

### 4.2 性能需求

1. 客户端一般操作响应时间 ≤ 1 秒,复杂查询 ≤ 3 秒;遇网络异常及时提示;
2. 支持多终端、多用户并行操作,**并发用户数 ≥ 50**;
3. 核心页面首屏加载时间 ≤ 3 秒;
4. 数据库常规查询响应 ≤ 1 秒(单表十万级数据下,借助索引与 Redis 缓存)。

### 4.3 产品质量需求

| 质量属性 | 要求 |
|---|---|
| 可靠性 | 关键操作(销售扣减、补货)具备事务保障,杜绝超卖与数据不一致 |
| 可用性 | 系统**可用性 ≥ 99.5%**,支持故障快速恢复 |
| 可维护性 | 前后端分离,模块化设计,代码规范,系统日志记录错误堆栈与操作上下文,便于排查 |
| 可扩展性 | 接口化设计,新增角色或模块时不影响既有功能;架构支持水平扩展 |
| 兼容性 | 兼容主流浏览器与操作系统 |

### 4.4 安全性需求

1. **密码加密**:用户密码采用 **BCrypt** 加盐加密存储,不以明文保存;
2. **登录保护**:连续 5 次密码错误锁定账号 30 分钟,登录接入图形验证码;
3. **操作审计**:记录登录日志与关键操作(增删改、销售扣减)日志,支持审计追溯;
4. **权限控制**:基于角色的访问控制(RBAC)结合行级数据隔离,每次请求校验角色与权限;
5. **SQL 注入与 XSS 防护**:采用参数化查询(MyBatis / MyBatis-Plus)与输入转义;
6. **会话安全**:JWT Token 设有效期,超时自动失效(如 30 分钟无操作),生产环境启用 HTTPS;
7. **数据删除**:采用逻辑删除(软删除),数据保留可追溯。

### 4.5 日志管理

| 日志类型 | 记录内容 | 保留时长 | 清理方式 |
|---|---|---|---|
| 登录日志 | 用户ID、登录时间、IP、登录结果 | 180 天 | 系统自动清理 |
| 操作日志 | 用户ID、操作时间、模块、操作类型、操作对象、变更前后数据 | 180 天 | 系统自动清理 |
| 错误日志 | 错误时间、错误类型、堆栈、请求参数、用户ID | 30 天 | 系统自动清理 |

### 4.6 开发、测试便利性(环境隔离)

为兼顾开发测试效率与生产安全,系统通过 **Spring Profile** 区分环境,**生产环境(`prod`)严格禁用**以下开发便利措施:

| 环境 | 措施 | 说明 |
|---|---|---|
| `dev`(开发 / 测试) | **万能验证码**:任意手机号 / 邮箱统一使用固定验证码(如 `888888`),并在控制台打印 | 免依赖真实短信 / 邮件网关;任意假号均可注册,无需囤积测试号或反复清库重发 |
| `prod`(生产) | 以上禁用,使用真实短信 / 邮件网关正常校验 | 由 `@Profile("!prod")` 与配置开关双重保障 |

> 本节为**实现 / 测试策略**,非业务需求,详细设计阶段落实。

## 5. 接口需求

### 5.1 外部接口

| 接口 | 用途 | 说明 | 本期状态 |
|---|---|---|---|
| **高德地图 JS API** | 销售点地图标注、医疗机构地图展示、地图选点获取经纬度 | 需申请 API Key(及安全密钥 `securityJsCode`);坐标系 **GCJ-02**;本地开发可用 `localhost` 域名白名单 | 本期实现 |
| (可选)短信 / 邮件接口 | 库存预警通知、审核 / 账号通知 | 接入第三方短信 / 邮件服务 | 二期实现 |
| (可选)医保政策数据源 | 同步最新医保政策 | 定时拉取或人工录入 | 二期实现 |

> **本期说明**:核心功能仅依赖高德地图 JS API 一个第三方服务;短信 / 邮件 / 医保接口均为二期扩展,不影响本期交付。

### 5.2 内部接口

内部接口采用 RESTful 设计,统一 JSON 格式交互。

| 规范项 | 说明 |
|---|---|
| 基础路径 | `/api/v1` |
| 请求方式 | GET(查询)、POST(新增)、PUT(修改)、DELETE(删除) |
| 认证方式 | `Authorization: Bearer {JWT Token}` |
| 响应格式 | `{ "code": 200, "message": "success", "data": {} }` |
| 分页参数 | `pageNum`(从 1 开始)、`pageSize` |
| 错误码 | 200 成功 / 400 参数错误 / 401 未授权 / 403 无权限 / 404 资源不存在 / 500 服务器错误 |

| 内部链路 | 协议 / 技术 | 说明 |
|---|---|---|
| 前端 ↔ 应用服务器 | RESTful / HTTPS + JSON | Vue 通过 Axios 调用后端,统一返回 `{code, message, data}` |
| 应用服务器 ↔ 数据库 | JDBC | MyBatis-Plus 持久层,HikariCP 连接池 |
| 应用服务器 ↔ Redis | Redis 协议 | 会话存储、热点数据缓存、库存预警状态 |

## 6. 附录

### 6.1 核心数据实体一览

> 本节为需求阶段的**概念数据模型**(实体 + 关系 + 关键属性),**不含字段类型与建表 DDL**,详细数据库设计在后续阶段进行。约定:主数据表统一带 `deleted`(逻辑删除)与 `create_time` / `update_time` 审计字段;字段以最终数据库设计文档为准。
>
> **二期扩展预留**(本期不实现,但建表时预留字段位,避免后续频繁改表):短信 / 邮件验证 → `user` 表可能新增 `email`、`phone`、`email_verified`、`phone_verified`;医保政策数据源 → `company_policy` 可能新增 `insurance_code`。
